開店前チェック

この帳場の使いかた(1周の流れ)

  1. 在庫で、仕入れたカードを登録する(仕入値と相場、枚数)
  2. 設計でオリパを組む。1口の値段・口数・中身を決め、還元率を見ながら調整
  3. 販売開始を押す。この時点で全口の中身が確定し、たねの指紋(コミット)が出る。これをSNSや商品ページに先に貼る
  4. 売り場でお客に番号を選んでもらい、引く。結果は自動で注文になる
  5. 注文で住所を控えて発送、追跡番号を入れて「発送済み」
  6. 売り切れたらたねを公開。お客は検算画面で中身を検証できる
  7. 帳簿で、売上・原価・粗利を締める

還元率と原価率のちがい

還元率 = 封入したカードの相場合計 ÷ 売上(1口の値段 × 口数)。お客から見た「戻ってくる割合」です。
原価率 = 封入したカードの仕入値合計 ÷ 売上。自分の懐から見た割合です。

相場より安く仕入れられていれば、原価率は還元率より低くなり、その差が粗利になります。 還元率が100%を超えていても、原価率が100%未満なら店は黒字になり得ます(実際そこが勝負どころです)。 逆に相場でしか仕入れられていないなら、還元率を上げるほど直に赤字です。

目安として、還元率50%を下回るとお客の評判は続きません。80〜95%あたりに置いて、 仕入れの安さ(=原価率)で利益を取る設計が、いちばん長持ちします。

封入の公正さを、どう証明するか

「あとから中身を抜いていないか」は、お客からは見えません。この帳場はコミット&リビールという手順で証明します。

  1. 販売前に、中身の並び順を決める乱数のたねを作る(64桁の16進)
  2. そのたねを SHA-256 でつぶしたコミットを先に公開する。たね自体はまだ伏せる
  3. 販売中は中身を変えられない(変えればコミットと合わなくなる)
  4. 売り切れ後にたねを公開。誰でも「封入表 + たね」から並び順を再計算し、実際に出たものと突き合わせられる

並べかたの決まり(第三者が別の言語で書き直せるように、そのまま書いておきます):

  • 公開した封入表の上から順に、枚数ぶん展開して配列 A を作る(長さ = 口数)
  • 乱数は SHA256(seed + ":" + i) (i = 0,1,2,…)の出力32バイトを、先頭から4バイトずつ32bit整数として使う
  • Fisher–Yates で k = n-1 から 1 まで: j を [0,k] の一様乱数にする。lim = floor(2^32 / (k+1)) * (k+1) とし、 取り出した r が lim 以上なら捨てて次の乱数へ(偏りをなくすため)。j = r mod (k+1)。A[k] と A[j] を交換
  • できた A の先頭が1口目、次が2口目…

ハッシュ・並べかたとも、この画面の検算タブでそのまま動きます。

法律まわり(専門家に必ず確認してください)

以下は「調べるべき論点の一覧」です。法律の助言ではありません。開業前に、古物商は警察署(公安委員会)、 表示や決済は弁護士・行政書士に確認してください。

  • 古物商許可 — 中古カードを買い取って売るなら必要。無許可営業は刑事罰。ネット販売なら「URLの届出」も要る
  • 特定商取引法に基づく表記 — 通信販売なら、氏名・住所・電話・代金・送料・引渡時期・返品の可否を明示。個人でも省略できません
  • 景品表示法 — 「高還元」「〇〇確定」は根拠が要る(優良誤認・有利誤認)。排出確率と封入枚数、残数は正しく出す。この帳場が確率表を自動生成するのはこのため
  • 賭博罪の線引き — 「必ず商品が届く物販」であることが生命線。店が自分で買い戻す(換金する)と、賭博・景品交換とみなされる危険が跳ね上がります。買取は必ず別の話にする
  • 資金決済法 — 先にポイントを買わせる方式は「前払式支払手段」に当たり、未使用残高が基準日に1000万円を超えると供託・届出の義務。都度払い(引くたびに決済)にすればこの論点を避けやすい
  • 年齢確認 — 未成年の高額購入はトラブルの筆頭。年齢確認と1回・1日の上限額を必ず入れる
  • 決済代行の審査 — オリパはギャンブル類似として断られることがある。契約前に業態を正直に申告する
  • 知的財産 — カード画像の無断掲載は権利者の許諾が必要な場合がある。自分で撮った写真を使い、公式ロゴは使わない

この単一HTMLでできること / できないこと

できる — 在庫と原価の管理、封入設計と還元率計算、公正な抽選と検算、対面・イベントでの実売、当選と発送の台帳、収支。 店頭やイベントの「その場で引いてもらう」形式なら、これ1本で実運営できます。

できない — 不特定多数がネット越しに同時に引くこと、クレジット決済、会員登録、住所の自動収集。 これらはサーバが要ります。移植の設計は下に書きました。

Web公開版に移すときの設計(そのまま発注書に使えます)

  • 構成 — Next.js(App Router) + PostgreSQL + Stripe Checkout。抽選は必ずサーバ側で行う。クライアントに封入表の中身を先に送らない
  • テーブル — cards(在庫) / oripas(価格・口数・状態・commit・seedは販売終了まで非公開列) / packs(口番号・card_id・order_id、UNIQUE(oripa_id,no)) / orders / shipments / ledger
  • 引く処理 — 1トランザクション内で SELECT ... FOR UPDATE により口番号をロック → 決済確定 → packs.order_id を埋める。二重販売はDBのユニーク制約で止める
  • 決済 — Stripe Checkout の webhook(checkout.session.completed)で確定。冪等キーを付け、webhookの署名を必ず検証
  • 公正さ — 販売開始時に commit を公開ページに載せ、完売時に seed を自動公開。検算ページは本ファイルの実装をそのまま移植
  • 表示義務 — 特商法表記ページ、排出確率表(自動生成)、残数のリアルタイム表示、発送目安、年齢確認
  • 運用 — 発送は注文CSVを吐いてラベル印刷。追跡番号の一括取り込み

データの置き場所

入力したものはこの端末のブラウザ内(localStorage)だけに保存され、外へは一切送りません。 端末を替えるとき・バックアップを取るときは、在庫 → 入出力 からJSONで書き出し / 読み込みできます。 ブラウザの履歴消去で消えるので、週に一度は書き出してください。
